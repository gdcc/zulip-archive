AI generated TL;DR — "The Practical Test Pyramid" (Ham Vocke, 2018)

Shape the suite like a pyramid: lots of fast unit tests → some integration/contract tests → very few
E2E. Avoid the ice-cream cone (slow, flaky, unmaintainable). Layer names don't matter much;
granularity + count ratios do.

  • Unit — most tests, no DB/FS/network. Test observable behaviour, not implementation, or they break
    on every refactor. Skip trivial code. Wanting to test a private method = SRP violation, extract a
    class.

  • Integration — one boundary at a time (DB, REST, queues, files). Run deps locally; fake third
    parties with WireMock via test config. Never hit prod. Fakes drift from reality → next item.

  • Contract (Pact/CDC) — consumer writes tests for only what it needs, publishes a pact file, provider
    runs it in their pipeline continuously. Kills cross-team API drift and gold-plating. Replaces the
    WireMock test, doesn't duplicate it.

  • E2E — max confidence, worst cost: flaky, slow, no clear owner in a microservices org. Keep to the
    1–3 journeys that carry core product value. Subcutaneous tests (REST-assured, just under the UI)
    get most of the value with less pain.

  • Acceptance tests (given/when/then) are about user correctness, orthogonal to the pyramid — write
    them as low as the scenario allows. Exploratory testing for what automation misses; automate each
    bug found.

Rules of thumb: Arrange–Act–Assert everywhere; one condition per test; readability beats DRY (DAMP,
Rule of Three); test code deserves production-grade care; order pipeline stages by speed, not test
type; push tests down and delete high-level ones already covered below. Terminology is irreparably
ambiguous — agree on definitions within your team and move on.
