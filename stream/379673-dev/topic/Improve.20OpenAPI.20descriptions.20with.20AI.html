Oliver Bertuch (Sep 15 2026 at 15:11):

Hey @Balázs Pataki what is the motivation behind getting the score back up? Looking at the PR I'm a little worried. While the score may get back up (quantitativly), it's not a qualitative improvement of our OpenAPI spec.

As the way our Java REST API endpoints responds has grown organically (one might even say out of control) towards not using DTOs, there's not a lot of schema that we can add now to the spec. On the other hand, that's one of the most essential things a client needs when using the spec to implement some action against the API.

So while the score is back up, the client will not have a lot of more information. The schema will literally say "expect a JSON object" and so on. I'm not sure this will help anyone. It's like code coverage: a high number doesn't tell you of what quality the test are made, how well they cover edge cases etc.

My vote would be to be honest and stick with a 89. It's not too bad, but looking at a 98 and then getting a lot of nothing seems contraproductive as an expectation to set and communicate.

That said: I very much fear it will be a lot of work digging ourselves out of the hole we dug... (But that's true for a lot of things gone wrong with the API architecture.)

Oliver Bertuch (Sep 15 2026 at 15:18):

I've invested a few tokens a while ago by asking Qwen3.8-Flash-Next to review the API Datasets class (was testing the LLM deployment on a server). A god class example par excellence with 7000 lines. Takes ~60kT / ~500MB of KV context cache to dig through. The TL;DR for a refactoring was:

  1. Split into focused resource classes (or sub-resources): DatasetResource, DatasetVersionResource, FileEmbargoResource, FileRetentionResource, GlobusTransferResource, DatasetTypeResource, CurationStatusResource, ThumbnailsResource, etc. A base AbstractDatasetResource can hold the shared findDatasetOrDie / response(…) helpers.
  2. Extract the per-file attribute logic (embargo, retention) into a shared generic helper or a small service.
  3. Standardize on one dataset-lookup pattern, one permission-check pattern, and one error-response pattern.
  4. Move handleVersion + DsVersionHandler into a package-level utility.
  5. Standardize parameter names ({id} everywhere for the dataset identifier).
  6. Reduce injected dependencies per class to only what each sub-resource needs.
  7. Break long methods into validation / orchestration / response steps.

The class is clearly functional (it's a production API for a real system), but from a maintainability and testability standpoint it is far from well-designed.

And it's not even mentioning response schemas, as the other tasks are far more important and complex... :see_no_evil: I might do this again and throw GitNexus into the mix, so the model has a better chance at understanding the Dataverse codebase context (haha).

Balázs Pataki (Sep 15 2026 at 15:41):

Yes, the current fix is to explicitly declare that we return "an object", although we don't specify its shape. The regression was that it didn't even say that it was "an object" and now it does . The vacuum score is not about how nice your API is functionally (I mean, whether you return a nicely shaped object or just an opaque object type), but whether it is properly defined so that it is machine interpretable. That's why I think 98 is reasonable with our current implementation and fix.

Of course the real solution - as I also suggested in the issue - is to have proper DTO-s returned, which then SmallRye will define proper JSON schemas for and so users would know the exact shape of the returned values.

Until then I think it is a valid and honest declaration that we return "an object" or "a string" and it is still more useful and correct than saying nothing.

So, my openapi enhancement attempts just tried to document what we have with more (human) descriptions without changing any API-s. In this respect with all these nicer description, we are of course nearly as bad with most of the input-output semantics as before.

For example, we have this endpoint:

            description = "Changes whether a dataverse is a metadata-block-facet root.")
    @RequestBody(description = "Boolean text indicating whether the dataverse is a metadata-block-facet root.")
    public Response updateMetadataBlockFacetsRoot(@Context ContainerRequestContext crc,
            @Parameter(description = "Dataverse alias, id, or persistent identifier.", required = true)
            @PathParam("identifier") String dvIdtf,
            @RequestBody(description = "Boolean text indicating whether the dataverse is a metadata-block-facet root.")
            String body) {
        try {
            final boolean blockFacetsRoot = parseBooleanOrDie(body);

These were already defined:

    @POST
    @AuthRequired
    @Path("{identifier}/metadatablockfacets/isRoot")
    @Consumes(MediaType.APPLICATION_JSON)
    @Produces(MediaType.APPLICATION_JSON)

But then in code we have

which clearly doesn't expect a JSON as input but a true or false or similar string value.

What I want to say is that a good vacuum value do not mean a semantically correct API, but conformance to OpenAPI spec.
