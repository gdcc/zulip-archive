Oliver Bertuch (Oct 14 2026 at 21:25):

My vision here is somewhat different. I want to be able to run something likemvn verify -Dit.groups=api to simply run all the API tests in one go.

Oliver Bertuch (Oct 14 2026 at 21:26):

The problem: we are using "IT" as a suffix for everything.

Oliver Bertuch (Oct 14 2026 at 21:27):

Technically, you can do whatever you want. For good practice, unit tests usually end in "Test" and any kind of "integration" test ends in IT. Units tests get run by Maven Surefire, typically bound to the Maven "test" phase.

Oliver Bertuch (Oct 14 2026 at 21:28):

Any "IT" by default is to be executed by Maven Failsafe, typically bound to the "verify" phase. Of course, any of the two can ran any test.

Oliver Bertuch (Oct 14 2026 at 21:29):

The difference is in how they handle executing the tests: https://www.baeldung.com/maven-surefire-vs-failsafe

Oliver Bertuch (Oct 14 2026 at 21:29):

IMHO we should start adopting good practices and not fight the ecosystem, but move with it.

Oliver Bertuch (Oct 14 2026 at 21:30):

Using Failsafe's default configuration to auto-discover any "*IT" classes and execute them is getting in the way for us.

Oliver Bertuch (Oct 14 2026 at 21:31):

While for self-contained tests in the groups "performance", "integration", etc I made sure they can just be picked up, the same is not true for API tests.

Oliver Bertuch (Oct 14 2026 at 21:31):

They require setting up the test instance first, before executing the tests.

Oliver Bertuch (Oct 14 2026 at 21:32):

Eventually, I would very much prefer using something inside Maven or JUnit to setup this stack automatically before executing the tests.

Oliver Bertuch (Oct 14 2026 at 21:32):

But we are not there (yet).

Oliver Bertuch (Oct 14 2026 at 21:32):

So while I agree auto-discovery would be superb, we kind of have to live with our self-inflicted limitations.

Oliver Bertuch (Oct 14 2026 at 21:34):

But even if we do auto-discovery, I totally would want to enable people just to run a selective set of tests. Not every test needs to be run all the time on local development, but maybe you want the full set of integration tests now. IMHO it would be nice to still keep these categories alive, but as an addition, not a requirement.

Oliver Bertuch (Oct 14 2026 at 21:36):

So how about this: we do auto-discovery, but with a second Failsafe configuration. We invent a new coding standard by calling our API tests just that. Something like DatasetAT or ApiTestDataset or DatasetTestApi. (Not using IT or Test as a suffix would be crucial to avoid the necessity to declare more complex regex for surefire/failsafe).

Oliver Bertuch (Oct 14 2026 at 21:37):

That way we get autodiscovery any time someone adds an API test where they don't need to put Tags on things (after all they were meant for more meaningful grouping than just test category).

Oliver Bertuch (Oct 14 2026 at 21:38):

We can make the Maven configurations have their own skips, following the established patterns.

Oliver Bertuch (Oct 14 2026 at 21:39):

This is all independent of Maven profiles (which we can use to do all sorts of crazy things)

Oliver Bertuch (Oct 14 2026 at 21:46):

We could even be so bold to use Maven phases to our advantage! Looking at the default lifecycle, we could bind running any "IT" to the "integration-test" phase and bind any "AT" to the "verify" phase. That would totally be inline with the tooling and good practices. Also, if we ever enable using a Maven/JUnit controlled stack deployment, that totally could be bound to any of the intermediate phases.

Oliver Bertuch (Oct 14 2026 at 21:49):

Just to give an example: using the Docker Maven Plugin (or any other plugin that steers containers, like the Docker Compose plugin) we can spin up a compose stack in "post-integration-test" and let any API tests "attack" it in "verify". That's cheap and easy to do, not involving any more complicated testcontainers setup.

Ash Manda (Oct 14 2026 at 23:59):

Thank you for your detailed response. This makes a lot of sense to me. I agree with the plan, both don't have to be mutually exclusive. Few caveats.

Number one, This means enforcing some kind of standard to developers that they have to manually name classes *AT. If say out of habit they name an API test *IT, and we aren't actively looking for it in the code review phase, it's going to slip by, CI is going to ignore it, and nobody will know.

Number two, My biggest problem with mvn verify has been that it runs the mvn package step. Assuming this is how our testing pipeline is going to be going forward: https://github.com/IQSS/dataverse/pull/12783 mvn verify kills the one thing that I intended to give from this PR which is time savings. In that specific PR, verify when tested rewrote the mounted /target/dataverse container. Until the stack setup itself moves fully into maven, we might have to make some tradeoffs here in terms of best practices and intended lifecycles.

Number three, merge conflicts. Anyone who's actively editing one of these API test classes now is going to be in for a rude shock. We'll have to inform people ahead of time.

So, here's what I might target in scope for three PRs:

  1. PR for Dataverse. I will rename the 56 (or 74?) classes to *AT or a different suffix/prefix as the team prefers it to be. Please do let me know if there's a preference. Some triage might be required here. I will add a ci-api-tests pom profile, and a second Failsafe configuration to detect *AT classes. I will add an exclusion marker for tests that don't run in CI. I will not remove the integration-tests.txt file just yet. I will rename the IT classes to AT for backwards compatibility reasons within the .txt file.
  2. PR for Dataverse Ansible. If we remove the .txt file immediately, it will break Dataverse Ansible for everyone. All of its branches that are used for older versions should be fine because they target specific tags. But I want to make a PR there and refactor the testing process so that when tested with develop, it doesn't fail.
  3. PR for Dataverse. At a later date, when downstream consumers seem to be working effectively, we nuke the integration-tests.txt file

Does this sound like a plan?
