Janvi Kapoor (Sep 10 2026 at 12:22):

Hi everyone,

I ran systematic tests on pyDataverse 0.4.0beta1 (commit 1fb1ac6) using Python 3.14.7 on Windows against demo.dataverse.org. Here is a summary of what I tested and the observations and errors I ran into:

Environment:

  • OS: Windows
  • Python Version: 3.14.7 (venv)
  • Target Server: demo.dataverse.org

Successful Operations:

  • Authentication & User Info: Successfully connected via NativeApi and retrieved user details (get_user).
  • Dataset Lifecycle: Created a draft dataset, fetched dataset details by DOI, retrieved persistent URLs and lock info, generated a private review URL, and fetched dataset versions/batch datasets.
  • Metadata & Exporters: Listed all available export formats and successfully exported draft metadata by explicitly specifying version=':draft'.
  • Collection Browsing: Crawled root collection contents using crawl_collection.

Observations, Warnings & Errors Noticed:

  1. Pydantic V2 Deprecation Warning:

    • Issue: Calling .json() on response objects triggered a deprecation warning:
      PydanticDeprecatedSince20: The json method is deprecated; use model_dump_json instead.

    • Note: Might need updating internally to align with Pydantic v2 standards.

  2. Draft Dataset Export (HTTP 400):

    • Issue: Calling get_dataset_export() on an unreleased/draft dataset without passing a version parameter resulted in:
      HTTP 400 - Unable to look up dataset based on version. Try :latest-published or :draft.

    • Note: Works fine when version=':draft' is passed explicitly.

  3. Strict Pydantic Validation on Metadata Edit:

    • Issue: Using edit_dataset_metadata raised strict validation errors when expected payload structures (like missing fields) weren't explicitly matched.

  4. Dataset Publication Rule (HTTP 409):

    • Issue: Attempting to publish a draft dataset via publish_dataset() returned:
      HTTP 409 - Dataset must have a valid license or Custom Terms Of Use configured before it can be published.

    • Note: Standard server-side validation rule, but noted for workflow testing.

While running edge-case and stress tests on pyDataverse 0.4.0beta1, I ran into one specific behavior in the collection crawler that might need a pre-flight validation check:

  1. Crawler Hang / Timeout on Invalid Filter Parameter:

    • Issue: When calling crawl_collection(":root", filter_by="invalid_filter_type"), the utility hangs indefinitely or causes an async network timeout instead of raising an immediate client-side validation error (like a ValueError).
    • Suggestion: Adding a quick input validation check for allowed filter types before initiating the async crawl process would prevent unnecessary network hangups.

Other standard validation checks (like Pydantic literal validation for QueryOptions and HTTP status mappings for invalid IDs/tokens) are behaving as expected.
