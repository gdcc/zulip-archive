Ash Manda (Nov 10 2026 at 16:34):

Hello and good afternoon!

I was monitoring one of the develop commits when I saw some tests failing due to a fringe missing ref, and then immediately afterward I noticed a merge commit was made into develop.

Although in this case, the failure occurred due to a simple missing reference, and could easily be resolved with a re-run (or in this case a merge), I was wondering what would happen if a PR got merged into develop, then the tests started failing, and multiple PRs were merged above it. Say test failed on commit 1, and commits 2, 3, 4 were merged back to back. It could happen for multiple reasons, say stale tests. Tests for commits 2, 3, 4 ran on a version of the develop branch where commit 1 didn't exist yet, and it could cause issues and conflict with 2 or 3 or 4.

In the current model, this will cancel all the tests supposed to run on 1, 2, 3, and the failure would only show up for commit #4 although in reality commit #4 was probably just fine. This could lead to valuable developer hours/business days wasted trying to pinpoint an issue that never existed in the first place.

I have an example here:

This could be solved either of two ways:

  1. Either let tests finish for older commits so that we know WHEN the tests started failing so we can pinpoint the exact commit to investigate from the get-go
  2. Block merging into develop until the tests for the current tip has finished.

I think this needs to be addressed ASAP. It looks fine until one day it isn't. What does everyone think?
